## Context

项目当前存在三组扩展点，但还没有统一插件边界：

1. `CardPageBlockType`、Pydantic `EnterpriseTemplateBlock` 和渲染适配器集中定义全部名片块。
2. 管理端路由/菜单与 FastAPI Router 在应用入口静态装配。
3. AI 子系统已经使用 `ChatProvider`、`EmbeddingProvider` 等协议，Worker 也已有事件处理注册表雏形。

本期选择名片块作为最小可验证纵向切片。它同时经过配置编辑、权限校验、资源解析、草稿/发布、公共 API 和访客渲染，足以验证插件平台合同，又不需要立刻把整个模块化单体改造成动态微内核。

## Goals / Non-Goals

**Goals:**

- 新增一个内置名片块时，只增加插件实现和注册，不修改核心块联合、核心渲染分支或大型集中式字段模型。
- 同一插件身份和版本贯穿公共端、管理端与 API，发布快照能够确定性重放。
- 企业只能启用平台允许的插件，并显式授予插件声明的能力；插件所有数据读取仍受 company/tenant 作用域约束。
- 平台可以给企业分配套餐并逐项打开或关闭商业能力；菜单可见性、公共展示和 API 授权必须来自同一最终权益结果。
- 旧页面块、旧草稿和旧发布快照无损可读，迁移可逐卡、可回滚。
- FAQ 与快捷入口成为可独立测试、启停和降级的样板插件。

**Non-Goals:**

- 第三方在线上传 JavaScript、Python、CSS、HTML 或数据库迁移。
- 本期引入 Module Federation、远程 ESM、iframe SDK、插件市场、在线支付、自动续费或跨版本热更新。
- 把 tenant、身份、RBAC、隐私同意、审计、发布引擎和资源安全变成可卸载插件。
- 本期迁移管理后台所有页面、FastAPI 全部 Router、Worker 任务或企微/微信集成。
- 允许插件直接取得数据库 Session、未裁剪访问令牌或跨租户数据集合。

## Decisions

### 1. 采用“稳定内核 + 受控贡献”而不是任意运行时代码

插件第一期是随平台构建、测试和部署的可信代码。平台可在运行时按企业启停插件，但不能从企业配置下载和执行新代码。这样可以先获得模块边界、按租户授权和独立升级能力，同时避免公共 H5 引入远程供应链和共享依赖风险。

前端使用构建时发现和异步 chunk；后端第一期使用显式注册表。未来若插件成为独立 Python distribution，可以在不改变宿主合同的前提下增加 entry-point 发现。

### 2. 插件清单是跨运行面的身份合同

每个插件声明一份规范化清单：

```json
{
  "schema_version": 1,
  "id": "cf.card.faq",
  "version": "1.0.0",
  "host_api": "1.x",
  "trust": "builtin",
  "permissions": ["knowledge.published.read"],
  "contributes": {
    "card_blocks": [
      {
        "id": "faq",
        "config_schema": "cf.card.faq/config/1"
      }
    ]
  }
}
```

构建和启动检查必须拒绝非法 ID、重复 `(plugin_id, version, contribution_id)`、不兼容宿主 API、缺少某个必需运行面实现或权限未声明。清单不保存密钥，也不允许声明任意可执行路径。

### 3. 页面文档引用插件贡献，插件配置由独立 Schema 验证

新页面文档使用 `schema_version: 2`，块的通用字段与插件字段分离：

```json
{
  "id": "faq-main",
  "plugin_id": "cf.card.faq",
  "plugin_version": "1.0.0",
  "contribution_id": "faq",
  "visible": true,
  "sort_order": 40,
  "directory_enabled": true,
  "config": {
    "mode": "selected",
    "document_ids": []
  }
}
```

通用宿主只校验块 ID、顺序、可见性、插件引用和大小限制。插件负责验证自身 `config`；服务端插件验证器始终是最终权威。配置 Schema 有稳定 ID，插件升级如改变持久化结构，必须提供纯函数式、可重复执行的配置迁移器。

### 4. 公共发布保存精确版本，运行时生成安全 Render Plan

草稿可以在管理员明确升级后迁移到新的插件版本；发布过程固定精确版本，完成以下步骤：

1. 检查插件版本在平台可用且企业已启用。
2. 检查权限授予覆盖插件声明。
3. 由插件验证配置和公司范围资源。
4. 归一化配置并写入不可变发布快照。
5. 公共读取在当前 tenant/company 上下文中解析允许的数据，生成只含展示所需字段的 Render Plan。

前端插件只接收 Render Plan 和宿主提供的受控动作，例如打开 AI、产品详情、案例详情或提交线索；不能接收管理端令牌、原始数据库标识集合或插件密钥。

### 5. 三个注册表共享身份，不共享运行时代码

- 公共端注册表：`plugin + contribution -> lazy renderer`。
- 管理端注册表：`plugin + contribution -> label/defaultConfig/editor/readiness`。
- API 注册表：`plugin + contribution -> validator/normalizer/resolver/permission requirements`。

注册表通过同一清单生成的索引校验一致性。React 和 Python 不直接互相导入，也不把前端类型当作安全边界。OpenAPI/JSON Schema 负责序列化合同，跨运行面合同测试负责防止漂移。

### 6. 宿主能力以最小授权句柄提供

插件不能直接访问全局服务。宿主根据清单和企业授予构造能力句柄，例如：

- `knowledge.published.read`
- `public_action.open`
- `analytics.emit`
- `catalog.published.read`
- `lead.create`

能力句柄自动绑定 tenant/company、审计上下文、超时和结果上限。插件未声明、企业未授予或平台停用的能力调用必须失败关闭，不得静默扩大权限。

### 7. Identity 是系统贡献，FAQ 与快捷入口是一期样板

`identity` 进入系统注册表但标记为 `required/system`：每份页面文档必须恰好一个、始终可见、不可被企业卸载。这样保持“全部由注册表运行”的技术一致性，同时不牺牲名片身份可靠性。

FAQ 插件验证知识文档选择并通过 `knowledge.published.read` 解析已发布问答；快捷入口插件验证 HTTPS、内部路径和电话动作，但不申请知识权限。两个插件故意覆盖“需要领域数据解析”和“纯配置动作”两类典型插件。

### 8. 兼容层是只读确定性适配器

现有 `schema_version: 1` 页面块在读取时映射为固定插件身份：

- `identity` -> `cf.system.identity@1.0.0`
- `faq` -> `cf.card.faq@1.0.0`
- `action_collection` -> `cf.card.actions@1.0.0`
- 其他块暂映射到 `cf.legacy.card-blocks@1.0.0`

兼容适配器不得依赖数据库当前状态改变结构，不得覆盖历史快照。编辑旧草稿时可以显式“升级为插件文档”；旧发布快照继续通过适配器服务，直到对应卡片重新发布。

### 9. 停用分为企业停用和平台紧急熔断

企业停用阻止新草稿添加和新版本发布；已经发布的可选插件默认继续按固定版本服务，避免企业操作意外破坏线上名片。平台紧急熔断可以立即阻止公共解析：可选块隐藏并记录降级，系统块使用平台安全兜底。恢复后固定快照无需重新发布即可继续运行。

删除插件版本不是正常操作。只要仍有发布快照引用，版本必须保留为可解析或兼容实现。

### 10. 商业权益在插件安装之上统一裁决

平台维护稳定的商业功能 ID 和三个默认套餐。企业保存 `plan_code`、计费周期、可选合同价格及 `feature_overrides`；解析顺序为“套餐默认 → 企业覆盖 → 系统必需能力”。没有显式商业配置的历史企业默认保持企业版能力，防止升级时意外关停；新开企业显式使用基础版。

企业管理员只能读取最终权益，平台管理员才能修改。后台菜单和直接路由根据最终权益隐藏或阻止访问，服务端仍以 `FEATURE_NOT_ENTITLED` 做最终拒绝。公开 AI 对话、线索、微信授权和名片区块同样在服务端检查，不能依赖前端按钮。

每个可选名片插件声明 `commercial_feature_id`。插件有效状态同时要求“商业权益已开通 + 企业安装已启用 + 权限授予完整 + 平台版本可用”；商业关闭优先于企业插件启用。

## Data Model

第一期新增或等价实现以下平台事实：

- `plugin_releases`: 插件 ID、版本、宿主 API、状态、清单摘要、发布时间。
- `company_plugin_installations`: company、插件 ID、启用版本范围、状态、权限授予、乐观版本。
- `Company.settings.commercial_entitlements`: 套餐、计费周期、合同价格、企业功能覆盖和额度覆盖；最终功能与额度为计算结果，不重复持久化。额度覆盖中缺省表示跟随套餐、非负整数表示企业专属额度、`null` 表示不限。
- 页面草稿/发布快照：保存精确插件引用与归一化配置。
- 审计记录：安装、启用、授权、配置升级、发布、企业停用、平台熔断和恢复。

插件代码随应用部署，数据库记录不充当代码下载地址。插件自有领域数据继续使用现有受 RLS 保护的业务表；本期不允许插件创建任意每租户表。

## Risks / Trade-offs

- [插件抽象把简单代码变复杂] → 只抽取实际跨三运行面的扩展合同，以两个差异化样板验证，不先迁移全部模块。
- [Python 与 TypeScript 合同漂移] → 单一清单/Schema 索引、构建检查和公共 fixture 合同测试。
- [发布快照引用的插件版本被删除] → 禁止删除被引用版本，使用状态机和引用检查，只允许停用或熔断。
- [插件解析造成 N+1 和首屏变慢] → API 按贡献批量解析，前端只懒加载当前页面使用的 chunk，并设置公共性能预算。
- [插件获得过宽权限] → 显式能力声明、企业授予、宿主作用域句柄和负向越权测试。
- [旧卡迁移导致视觉差异] → 只读兼容投影、金丝雀启用、视觉回归和逐卡重新发布。
- [平台紧急熔断破坏页面结构] → 系统块必须有核心兜底；可选块省略时目录与排序重新从 Render Plan 派生。

## Migration Plan

1. 增加插件清单、注册表和 `schema_version: 2` 合同，不改变现有读写路径。
2. 注册 identity 系统贡献、FAQ 和快捷入口样板，实现 v1 到 v2 的只读适配器和合同测试。
3. 在编辑器和公共渲染器后增加按卡片/企业控制的插件宿主开关，双路径输出对比但仍以旧路径为默认。
4. 启用新草稿写入和插件发布检查；旧发布快照继续兼容读取。
5. 对试点企业启用插件路径，完成发布、回滚、熔断、移动端和跨租户验证后再扩大范围。
6. 回滚时关闭插件宿主开关并恢复旧写入路径；保留所有新增记录和 v2 文档，不做破坏性降级迁移。
7. 商业权益回滚只移除企业显式配置；历史企业回到兼容的企业版默认，新企业创建仍须显式套餐，任何回滚不得绕过服务端权限和租户边界。

## Open Questions

- 企业停用是否应提供“立即从公开名片隐藏”选项？一期采用仅阻止新发布；需要即时隐藏时由平台紧急熔断处理。
- 插件升级是企业逐个确认，还是平台提供兼容版本自动升级？一期只允许管理员显式升级草稿，发布快照永不自动迁移。
- 后续第一个跨名片块插件面应优先迁移后台页面、AI Provider 还是企微集成？待一期样板的复杂度和运行指标验证后决定。
- 套餐公开标价、优惠、试用、到期与自动降级由后续 Billing 域管理；本期合同价格只作为平台运营配置，不触发扣款。
